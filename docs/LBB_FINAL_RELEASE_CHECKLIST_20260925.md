# آماده‌سازی انتشار اصلاحات LBB

وضعیت: فقط شاخه‌های کد؛ تا اجرای آزمون‌های بک‌اند و تأیید وضعیت واقعی Production، انتشار ممنوع است.

## دروازه‌های آزمون

1. Frontend: `npm run typecheck`، `npm run lint`، Build با `NITRO_PRESET=node-server`، نمایش SSR مسیرهای اصلی و مرور موبایل و دسکتاپ.
2. Backend در محیط جدا با PHP 8.3 و Composer: `php artisan test`، آزمون Migration up/down روی کپی دیتابیس، آزمون Formهای Filament و انتخاب رسانه برای محصول/مقاله/دسته/گالری. فایل‌های عمومی و WebP بعد از آپلود واقعی بررسی شوند.
3. Web Push: کلیدهای VAPID در محیط آزمایشی؛ رضایت صریح مهمان و کاربر، لغو رضایت، جلوگیری از انتقال اشتراک متعلق به شخص دیگر، صف کمپین موضوعی، جلوگیری از ارسال پس از لغو رضایت و ارسال آزمایشی در مرورگر واقعی.
4. Noindex: هدر `X-Robots-Tag` روی ورود و مسیرهای داخلی `/admin` بررسی شود؛ `robots.txt` نباید دسترسی خزنده به این هدر را مسدود کند.
5. جریان پرداخت و سفارش قبلاً قبول شده و بدون نیاز مشخص دوباره اجرا نشود؛ تغییرات این شاخه نباید مسیرهای آن را تغییر دهند.

## Backup و Canary

- ابتدا SHA، سرویس‌ها، Symlinkهای فعال و Cron/Scheduler را **فقط بخوانید**. تشخیص سفارش منقضی مستقل از این انتشار است؛ `schedule:run` و فرمان انقضا پیش از تشخیص اجرا نشوند.
- پیش از Migration، Backup کامل سازگار MySQL همراه با checksum و آزمون Restore روی دیتابیس جدا، Backup پوشه `storage/app/public` و نسخه تنظیمات و Releaseهای فعال تهیه شود. JSON تنظیمات قبلی جایگزین Backup دیتابیس نیست.
- Migration روی کپی دیتابیس اجرا و فرم‌های موجود بررسی شود. ساخت Release جدید بر اساس SHA انجام شود؛ Release فعال in-place تغییر نکند.
- Frontend را با Build جدا و `NITRO_PRESET=node-server` روی پورت Canary بالا بیاورید؛ API و ۱۳ مسیر ثبت‌شده در handoff، favicon فرانت و بک‌اند، موبایل، گالری و فوتر را بررسی کنید. Backend Canary با دیتابیس جدا و کلیدهای آزمایشی Push اجرا شود تا هیچ اعلان واقعی ناخواسته ارسال نشود.
- فقط پس از عبور از دروازه‌ها و ثبت نتیجه، جابه‌جایی اتمیک Symlink و بررسی سلامت سرویس‌ها و HTTP عمومی انجام شود. `php artisan optimize:clear` روی Production اجرا نشود.

## Rollback

- SHA و مسیر Release قبلی را نگه دارید؛ Symlink فرانت و بک‌اند را اتمیک به Release قبلی برگردانید و سرویس‌ها را راه‌اندازی مجدد و سلامت را بررسی کنید.
- تغییرات دیتابیس را کورکورانه با `migrate:rollback` برنگردانید: وجود اشتراک‌های مهمان و `gallery_items.image_url` خالی باید ابتدا بررسی شود. برای بازگشت داده از Backup تست‌شده استفاده کنید. فایل‌های رسانهٔ تازه را تا تکمیل بررسی حفظ کنید.
- اعلان‌های کمپینِ صف‌شده قبل از Rollback باید شناسایی و از ارسال ناخواسته جلوگیری شود؛ هیچ فرمان ارسال یا انقضای دستی جزو این رویه نیست.
